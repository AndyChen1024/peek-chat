# Harness Engineering: Leveraging Codex in an Agent-First World

> 原文：[openai.com/index/harness-engineering](https://openai.com/index/harness-engineering/)
> 翻译日期：2026-02
> 这是 OpenAI 官方关于完全用 AI Agent 构建软件产品的实践报告，是本项目的核心方法论参考。

---

## 实验规模

过去五个月，OpenAI 团队构建了一款软件产品的内部 beta 版，**其中没有一行代码是人工编写的**。

- **3 人团队**（后扩至 7 人），从空 Git 仓库开始
- 约 **100 万行代码**，约 **1500 个 PR**
- 平均每人每天 **3.5 个 PR**
- 产品已有数百名内测用户
- 估计用时约为手工编写的 **1/10**

核心理念：**人类掌舵。智能体执行。不手动编写代码。**

---

## 一、工程师角色重新定义

工程师工作重点转向系统、架构和杠杆作用。

**遇到问题的思维方式转变**：
- ❌ 旧思维：「再努力一点」
- ✅ 新思维：「智能体还缺什么能力？如何让这个能力对智能体清晰可读且可强制执行？」

**工作流**：工程师描述任务 → 运行智能体 → 智能体打开 PR → Codex 自审 → 请求额外智能体审查 → 响应反馈 → 循环直到所有审查通过。

人类可以审核 PR，但并非必须。几乎所有审核已调整为智能体对智能体。

---

## 二、提高应用程序的可读性

让应用对 AI Agent 直接可读：
- 应用支持 git worktree 启动 → Codex 可为每次更改启动独立实例
- Chrome DevTools 协议接入智能体运行时 → DOM 快照、截图、导航
- 本地可观测性栈（LogQL + PromQL）→ 智能体可直接查询日志和指标

**效果**：单次 Codex 运行可在单个任务上持续工作超过 6 小时（通常在人类睡眠时间）。

---

## 三、代码仓库 = 记录系统

**核心教训：给 Codex 一张地图，而不是一本 1000 页的说明书。**

大号 AGENTS.md 的失败原因：
1. 情境是稀缺资源，巨大指令文件挤掉任务和代码
2. 过度指导反而无效——当一切都「重要」时，一切都不重要
3. 它会立即腐烂，变成陈旧规则的坟场
4. 单个 blob 不适合机械检查

**正确做法**：
- `AGENTS.md` ≈ 100 行，用作**地图**，指向 `docs/` 中的深层信息
- 知识库结构化存放：架构文档、设计文档、执行计划、技术债务追踪器、产品规格
- 渐进式披露：智能体从小而稳定的切入点开始，被指导下一步该去哪里
- 严格执行：linter + CI 验证知识库新鲜度，定期「doc-gardening」智能体扫描过时文档

---

## 四、目标是智能体的可读性

**智能体在运行时无法在情境中访问的任何内容，都是不存在的。**

- Google Docs、聊天记录、人脑中的知识 = 不可访问
- 代码仓库中本地、已版本化的工件 = 唯一可见的信息源

这意味着：团队在 Slack 上达成的架构共识？如果智能体无法发现它，就等于不存在。

倾向于选择可完全内化于仓库中推理的依赖项和抽象。「枯燥」的技术因其可组合性、API 稳定性和训练集表现，对智能体更友好。

---

## 五、规范架构与品味

**通过强制执行不变量，而非微观管理实施过程。**

- 每个业务域划分为固定层（Types → Config → Repo → Service → Runtime → UI）
- 依赖方向严格验证，仅允许有限的边
- 横切关注点通过单一显式接口进入（Providers）
- 约束通过自定义 linter + 结构测试机械强制执行
- linter 错误信息中直接注入修复指令

> 在以人为本的工作流程中，这些规则可能迂腐。有了智能体，它们是倍增器：一旦编码，立即应用于所有地方。

在边界内，允许智能体在解决方案表达方式上有很大自由。人类品味通过审查评论、重构 PR、文档更新持续反馈到系统中。

---

## 六、吞吐量改变合并理念

- 尽量减少阻塞合并门
- PR 生命周期短
- 测试偶发失败通过后续重跑解决，而非无限阻碍
- **纠错成本低，而等待成本高**

---

## 七、智能体生成的完整范围

不只是产品代码——**整个代码仓库**：
- 产品代码与测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估框架
- 审阅评论和回复
- 管理代码仓库本身的脚本
- 生产仪表板定义文件

---

## 八、不断提高的自主水平

Codex 现在可端到端驱动新功能：验证代码库 → 重现漏洞 → 录制故障视频 → 实施修复 → 验证修复 → 录制解决方案视频 → 打开 PR → 回应反馈 → 合并。

---

## 九、熵与垃圾收集

**AI 会复现代码库中已存在的模式——包括不理想的模式，这不可避免导致漂移。**

- 最初人工每周五花 20% 时间清理「AI 残渣」→ 不可扩展
- 改进：将「黄金原则」直接编码到代码仓库
- 定期运行后台 Codex 任务扫描偏差、发起重构 PR
- 大多数 PR 可在一分钟内完成审查并自动合并

> 功能类似垃圾回收。技术债务如高息贷款：不断小额偿还，远好过累积后痛苦解决。

---

## 十、仍在学习的内容

不确定的问题：
- 在完全由智能体生成的系统中，架构连贯性如何随时间演变？
- 人类判断力在哪些方面能发挥最大作用？如何对其编码？
- 随着模型功能增强，系统将如何演变？

确定的结论：**构建软件仍然需要纪律，但纪律更多体现在支撑结构上，而非代码上。** 当前最棘手的挑战集中在设计环境、反馈回路和控制系统。

## 本项目中的应用

peek-chat 从第一天起就遵循了这篇文章的核心模式：

| 文章原则 | peek-chat 对应 |
|---------|---------------|
| AGENTS.md 是地图 | `AGENTS.md` ≈ 120行，指向 `docs/` |
| 结构化 docs/ | `docs/PRD.md` + `docs/ARCHITECTURE.md` + `docs/conventions.md` + `docs/testing.md` + `docs/HARNESS-ENGINEERING.md` |
| 渐进式披露 | PRD.md → ARCHITECTURE.md → 模块 → 执行计划 |
| 架构不变量 | 严格的包依赖方向（model ← 各包 ← ui ← apps） |
| 边界验证 | Module dependency flow 明确上墙 |
| 对智能体可读 | 全部知识在代码仓库内，无外部依赖 |
| Provider-agnostic | AiProvider 接口隔绝实现，Harness 接入零侵入 |
| 代码仓库 = 记录系统 | 完整 PRD + 架构 + 规范 + 测试策略 + 设计规格均在 docs/ 内 |
| 熵与垃圾收集 | `docs/tech-debt.md` 追踪债务，偿还计划明确 |
